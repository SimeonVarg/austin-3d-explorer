# Speed, 2026-10-09: measurement and plan (UNFINISHED, first push so the Rust and renderer studies can read it)

Status: draft written while the runs are still going. Every number says how it was taken. A number marked
"one sample" is one load and means little: this repo has measured 11 s to 65 s for the same page on a quiet machine.
Tools: `scripts/perf/` (`load-profile.mjs`, `frame-profile.mjs`, `apartment-buffers.mjs`, `lib/cpuprofile.mjs`).

## 1. Load breakdown (cold load, empty browser cache)

### 1a. First look: ONE SAMPLE, Mac, hardware graphics, no CPU throttle
Instrument settings: fresh headless Chrome 155, window 1280x800 at device pixel ratio 1.5, Intel Iris Plus 655
through ANGLE Metal, `?drift=0`, graphics auto-detect cancelled, `serve.py` (no compression), CPU throttle 1x
(none), machine load average 12.6 at the start and 30.3 at the end (the Mac was busy with other helpers: this
is a loaded machine, not a quiet one). One load, so no minimum and no spread yet.

| Moment | Time from navigation (ms) |
|---|---:|
| DOMContentLoaded (the page scripts are synchronous, so the DOM waits for them) | 4,853 |
| first paint | 10,208 |
| map object created | 11,513 |
| first map frame | 13,505 |
| map style loaded, first idle | 16,971 |
| authored apartments build finished | 46,288 |
| CITY READY (the loading veil lifts, the intro flight starts) | 79,355 |

What the app itself says about it: the veil waited 58,003 ms from its own start (reason reported: "ceiling"), the
authored apartments reported 198 buildings, 1,978 blocks, 16,654 faces, 644,425 cells, 3,116,469 triangles,
`count.ms` 45,161 over 39 time slices. `count.ms` is wall clock including the pauses between slices, not CPU.
The veil did not lift when the apartments finished (46.3 s) but 33 s later: the sources it waits for
(`austin-roads` first reported loaded at 58.2 s, `austin-entrances` at 60.5 s) were starved by the build, which
produced 173 tasks over 50 ms (76 s in total, the longest 6.6 s) on the main thread. Main-thread work in the
Chrome DevTools counters: script 50.7 s of 85.5 s task time (one sample).

Per-pass timers from the app's own functions (start time in the load, duration; one sample, 1x):
`initFacades` 2,402 ms at 17.0 s (paints every facade pattern for every tier at once, synchronous);
`initSky` 758 ms; `initGraphics` 326 ms; `applyGraphics` 341 ms at reveal; `initGround` 264 ms;
`applySlopesArt` 304 ms; `applySlopesApartments` 189 ms. Everything else under 70 ms.

"Wire" here is what the local server sent, which does not compress (`serve.py`), so it equals the raw size. The
gzip and brotli columns compress the same files from disk (gzip level 6, brotli quality 6) to show what a
compressing host sends; the production wire sizes are measured separately below when that run lands. The
biggest single files: `ground.geojson` 7.8 MB, `entrances.geojson` 6.5 MB, `norman-hackerman-building.json` 2.3 MB,
`roofs.geojson` 1.8 MB, `campus_landscape.json` 1.8 MB. **`roofs.geojson` was fetched twice in this load** (1.8 MB each),
which is a finding on its own (to confirm on more reps).

### 1c. Memory the page asks of WebGL at city ready (one sample, desktop, page-requested bytes counted in the page)
Textures ~690 MB (of which `js/facades.js` pattern atlases ~607 MB), buffers ~610 MB (three.js authored buildings
~484 MB, MapLibre ~46 MB, facades ~51 MB). Texture bytes include a 1.33x mip-chain allowance and may be an
overestimate; they are what the page asked for, not what the driver holds. JS heap used 146 MB.

## 5. What a Rust/WebAssembly version or a purpose-built renderer could save, per hot spot (best case), and what would have to be true
The verdict is left to the two studies (`~/Projects/flyover-rust`, `~/Projects/flyover-renderer`). This section is a first
draft from the first sample and the code, to be replaced with profile numbers.

| Hot spot (from 1a, one sample) | Where | Share of the load | Best case with Rust/wasm | What would have to be true |
|---|---|---|---|---|
| Apartment mesh build: 3.1 M triangles from specs, 45 s wall, ~39 slices | `js/slopes-apartments.js` (~3,400 lines of generator) plus `js/slopes.js` buffer assembly | the largest single block of main-thread time | JS to wasm for number-crunching loops is usually 2x to 5x; with typed arrays written in place (no per-vertex JS arrays) the best case is a 5x to 10x cut of this block | the generator is ported whole (it is hundreds of rules: skins, bays, balconies, roofs); the specs cross to wasm as bytes; the output buffers are written directly into wasm memory and handed to WebGL without a copy; the build can run in a worker (wasm has no DOM) |
| Facade pattern painting at boot | `js/facades.js` `initFacades` 2.4 s, then paced worker jobs | 2.4 s sync + worker time | pixel loops (premultiply, low-pass, mottle) are the wasm-friendly part, the canvas drawing calls are not (they are browser APIs) | pattern drawing is rewritten as pure pixel math instead of canvas2D calls |
| GPU draw time | three.js and MapLibre | not a load cost | none: wasm does not draw faster, only a different renderer design could (fewer draw calls, culling, level of detail) | see the renderer study |
| Network (48 MB cold, 41 MB of it data JSON) | server | the whole first 10 s on a slow link | none from wasm; a binary or tiled data format would, with or without Rust | |
