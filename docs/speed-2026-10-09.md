# Speed, 2026-10-09: measurement and plan

Where a cold load of the city goes, what a frame costs, what a phone must hold, and a ranked list of fixes with the
share of time or memory each one attacks. Written for the lead and for the two big-decision studies (Rust/WebAssembly in
`~/Projects/flyover-rust`, a custom renderer in `~/Projects/flyover-renderer`), which are asked to take their numbers from here.

**Read this first: which numbers to trust.**
- The only QUIET-machine numbers are from the AWS g6.2xlarge (NVIDIA L4, 8 vCPU, Linux, machine load average 2 to 6),
  run 38028735398 (the whole suite), and run 38026555146 (frame time). They have 3 reps (load) or 2 to 3 (frame) and the
  spread is shown. The 2019 MacBook Pro could not be measured quietly: the machine load average was 56 to 377 during my
  profiled loads (other helpers' browsers, and the shared browser queue made every other planned Mac run wait for over an
  hour), so Mac numbers here are labelled ONE SAMPLE and are for shape, not for seconds.
- An AWS L4 box is a faster CPU than the 2019 Intel laptop and has a far bigger GPU; the 4x CPU throttle on it stands for
  a phone (crudely: it slows only the page main thread, not workers, and not the GPU). Do not read either as an iPhone.
- Not measured at all: any real phone; parse/compile time (the trace run never got a browser slot); warm load on the Mac;
  per-frame CPU profile; frame time on the Mac. See section 7.

Tools: `scripts/perf/` (`load-profile.mjs`, `frame-profile.mjs`, `apartment-buffers.mjs`, `lib/cdp.mjs`, `lib/cpuprofile.mjs`,
`lib/instrument.js`), started on the AWS runner through the wrappers `scripts/verify/perf-*.mjs`. Raw profiles and JSON are in
`~/flyover-private/speed-2026-10-09/` (not in the repo). PR #435.

Three readings:
1. **The veil lifts 10.5 s (1x) and 31 s (4x) after the apartments are built.** The build is done at 12 s (1x) but the loader
   screen stays up until 23 s: at 1x `readyToReveal()` turned true 0.04 s after the source `campus-storeys` first reported loaded
   (23.13 s; that source is deliberately deferred, `js/facades.js` `CS.defer`, and the entrance doors, `austin-entrances`, landed at
   22.3 s), in all three 1x loads the reveal reason the app reports is `ceiling`, never `gate` (`gateOkAt` is null).
   At 4x the same wait is 31 s and the last source landed at 43.6 s, so the 4x wait is not explained by a source. This is the
   largest single lever on the time to "city ready" and it is a gate, not work (but the main thread is full of work during
   that window: see the phases in section 2). I did not change the gate.
2. **First paint is fast (0.5 s at 1x).** The wait is not the page, it is the city.
3. **Warm load is not much faster** (one 1x rep, local server with `max-age=600`): city ready at 19.9 s against 23.3 s cold,
   wire 2.0 MB against 48 MB. The load is bound by CPU work, not by the network. NOTE the production host sends
   `cache-control: public, max-age=0, must-revalidate` (checked with curl, 5 files), so a returning visitor on production
   revalidates every one of the ~280 requests, which the local `serve.py` (`max-age=600`) does not. Not measured.

Per-rep p50 West free: 8.1, 8.4, 8.1 ms (spread 0.3 ms), p95 10.1, 11.2, 9.6. Reading: on a good GPU a frame costs ~8 ms,
and **the JavaScript on the main thread costs ~8.2 ms of that**: the page is CPU-bound, not GPU-bound. Adding the GPU
wait (stall pass) adds only ~2 ms, so the GPU does ~2 ms of work per frame here. About 1,200 draw calls and 3 to 4.7 million
triangles are submitted every frame (this counts the shadow passes and MapLibre's layers together; the authored apartments
cull to 105 of 198 ranges, 2.2 M of 3.1 M triangles, in the sampled state). WebGL requested at the end: textures 798 MB
(`js/facades.js` pattern atlases 749 MB), buffers 649 MB (three.js authored buildings 487 MB, facades 84 MB, MapLibre 76 MB),
JS heap 289 MB, ArrayBuffer backing 597 MB. The "main thread busy 100%" column is true for any vsync-off run and says
only that the thread never waited.

What this does not tell: a 2019 Intel laptop GPU and a phone GPU have a fraction of an L4's fill rate and memory
bandwidth, so the GPU share there is larger than the ~2 ms seen here; the CPU share (8 ms on a fast Linux core) is
larger there too (a Mac laptop core is slower; the 4x throttle stands for a phone).

### 5b. Baking the apartment meshes: size against time (measured, desktop detail, `apartment-buffers.mjs`, AWS run 38028735398)
The page builds **6,529,917 vertices and 3,116,833 triangles in 198 buildings (25 meshes)**: **347.1 MB raw** (55.7 bytes a vertex), **32.2 MB gzipped**
(whole-mesh gzip at the browser's default level; per attribute: position 74.7 MB raw -> 13.3 MB gz, index 35.7 MB -> 16.7 MB gz, normal 74.7 -> 1.3 MB,
`aSurface` 99.6 MB -> 0.4 MB, three colour sets 18.7 MB each -> 0.2 to 0.3 MB, `aFacet` 6.2 MB -> 0.0). Per building: median 962 KB raw / 122 KB gzip
(8,730 triangles), largest 28.8 MB raw / 2.5 MB gzip (269,332 triangles), smallest 11 KB. For the median-size building brotli at quality 9 gives 80 KB against
122 KB gzip (position 206 K -> 49 K, index 102 K -> 23 K, normal 206 K -> 7 K, everything else -> under 1 K), so a baked file would be about 21 MB brotli for the
set at best (positions and indices are the whole cost), and perhaps 12 to 15 MB with 16-bit positions and delta-coded indices (an estimate, not built).
Against that, **the specs the build starts from are 54 JSON files: 18.8 MB raw, 3.5 MB gzip, 1.6 MB brotli (core and on-demand areas together).**
So baking trades the apartments build (4.2 s of main thread at 1x in the profile, 14 s wall clock with its pauses; 16 s inclusive at 4x) for **a download
about 7x to 13x the size of the specs it replaces**, on the very phones that are also slowest to download. Verdict from the numbers: baking wins on CPU and loses on bytes;
it only makes sense for the on-demand areas fetched later, or combined with the compact encoding above. The phone's built buffers (arrays are freed after upload
there, so `apartment-buffers.mjs --phone` could not read them, exit 1) are 262 MB on the GPU (section 4).

## 6. Rust/WebAssembly or a purpose-built renderer: what each hot spot could save in the best case, and what would have to be true
The verdict is left to the two studies (`~/Projects/flyover-rust`, `~/Projects/flyover-renderer`). Everything below is
my reading of the profile; **no wasm or Rust code was written or timed**, and the "best case" multipliers are
typical ranges for this kind of loop, not measurements from this repo.

| Hot spot (share of 1x main thread, one sample) | What the loop is | Best case with Rust/wasm | Best case with a purpose-built renderer | What would have to be true |
|---|---|---|---|---|
| `blurWrap` js/pattern-lowpass.js:60, 7.8% main (+ most of ~160 s of worker CPU) | box blur over RGBA typed arrays | 3x to 6x with SIMD in a worker pool; the cheapest wasm candidate: pure arithmetic, one buffer in, one out | none | the tile image is copied across the boundary (a few hundred KB each, a memcpy); the canvas drawing before it stays in JS; wasm SIMD is available in the target browsers (Safari 16.4+) |
| `drawRaw` / `drawTile` / `applyMottle` / `decimate` js/facades.js, ~6.4 s | canvas2D drawing calls plus pixel loops | only the pixel loops (`applyMottle`, `decimate`, ~1.4 + 0.7 s) | patterns drawn on the GPU in a shader would delete the CPU painting and the 600 to 750 MB of atlases | the drawing is rewritten as math, not canvas calls; for a renderer: a procedural facade shader reproduces today's patterns to the pixel gates |
| Mesh emission `push` `quad` `rgb` `rgb3` `g` `triN` `faceN` `dot` js/slopes.js, 14.9 s file self (13%) | per-vertex function calls pushing floats into arrays | 3x to 5x if the arrays become pre-sized typed arrays written from wasm; much of the gain is also available in plain JS (typed arrays, no per-vertex closures) | a GPU-generated mesh (compute) removes the CPU and the upload, WebGL has no compute | the generator that calls these moves with them (it is the bigger part of the cost); output stays visually identical to the gates |
| Apartment generator `tileFace` `windowsFromBays` `drawWall` js/slopes-apartments.js, 10.3 s self, 19.8 s inclusive | ~3,400 lines of rules over JSON specs, branchy, object-heavy | 1.5x to 3x (branchy object code gains less than arithmetic loops); a full port is weeks and ties the 48 building specs to a second language | instancing or GPU-side repetition of windows/bays would cut the 3.1 M triangles and the build together | the rules are frozen enough to port; the specs cross as bytes; the build can run in a worker (it cannot today: it uses three.js objects) |
| Campus trees js/campus-landscape.js, 7.8 s self | per-tree crown geometry | 3x to 5x | instancing makes it ~free | n/a: instancing in plain JS reaches the same end with no new language |
| GC 4.9% and `(program)` 4.6% | allocation churn, native work | falls if the above move to preallocated buffers | | |
| MapLibre main-thread code 22.9% (`clone`, protobuf decode, `readSVarint`) | a library | none from us (we do not own it); a different map engine or a native-style renderer in wasm is a different project | a purpose-built renderer would replace MapLibre and its 260 style layers and 1,200 draw calls | the basemap, tiles, labels and 95 `addLayer` sites are re-implemented |
| Frame time: JS 8.2 ms of an 8 ms frame (L4), ~1,200 draw calls | three.js + MapLibre submission | none: draw-call submission is the browser API, not arithmetic | the real prize if the CPU cost per frame is draw-call count: far fewer, larger draws; culling; instancing | the per-frame profile (not taken, see section 8) shows submission rather than JS logic dominates |
| `aeMeasure` / `aeGpuCollect` (graphics.js) | GPU readback + a small loop | none (readback latency) | | the fix is to run it less, in JS |
| Network (48 MB cold locally, 6.4 MB gzipped data), DOM, GPU fill | | none | a binary/tiled data format helps with or without Rust | |

Costs a wasm path must pay, with what the repo has today: no build step (a Rust toolchain adds one; the built `.wasm`
could be committed like `vendor/`); a wasm binary for these loops is small (tens to a couple of hundred KB gzipped; not
measured here); threads need cross-origin isolation headers (`COOP`/`COEP`), which would break the unpkg libraries
and third-party tiles, so use one wasm instance per worker; the facade workers are created from blobs, so a wasm module
has to be fetched and compiled in each.

## 7. What I could not measure, or am not sure of
- **Any real phone.** All "phone" numbers are desktop Chrome with a 4x main-thread throttle or mobile emulation, on an L4 server GPU. They rank changes; they do not predict an iPhone.
- **The Mac quietly.** Every Mac load ran at machine load average 12 to 377 (other helpers). The Mac's load-time minimum and spread over 5 reps do not exist; the quiet-box 3-rep table in 1a is the replacement. The Mac frame-time run, the Mac trace run and the phone-memory run on the Mac were queued for over an hour behind other jobs and never started.
- **Reps.** The load table has 3 reps per arm, not 5. Profiles are one sample per arm. The frame table has 3 reps (desktop) and 2 (phone).
- **JS parse/compile.** The tracing run (`--trace`) was built but never ran. The CPU profile shows no separate parse row, so "JS parse/compile" is NOT in the tables. `js/wayfind.js` parse cost is unknown.
- **Per-frame CPU profile.** Frame JS is 4.4 to 8.2 ms but which functions make it was not profiled.
- **Warm load** is one 1x load on the quiet box against the local server's `max-age=600`; production revalidates, so the production warm load is unmeasured.
- **Production transfer sizes** of the full cold load: only five files were checked with curl; the full-load production run was not done.
- **The 4x throttle** slows the page main thread only; workers (the facade pattern pool) keep full speed, so 4x understates a real phone's worker time.
- **The `aeMeasure` 55 s at 4x** (loaded Mac) did not reproduce on the quiet box.
- **GL byte counts** are what the page requested through `texImage2D`/`bufferData`/`texStorage2D` (mip chains estimated at 1.33x, `texStorage2D` assumed 4 bytes a pixel), not driver allocations.
- One 3-second headless Chrome was started on the Mac by hand (blank page, to test the WebSocket fallback) outside the `gpu-run.mjs` queue; everything else went through it.
